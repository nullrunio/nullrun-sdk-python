# NR-P004 — Indeterminate decision

| Field | Value |
|---|---|
| **Code** | `NR-P004` |
| **Category** | **P**rotocol |
| **Exception class** | `NullRunGateIndeterminateError` |
| **Retryable** | Yes |
| **Default `user_action`** | "The SDK could not obtain a decision from the NullRun gate: the call failed for a reason that is not a network failure, so the SDK stopped rather than assume the call was allowed. This is usually an SDK-side fault — retry, and if it persists, report the exception's cause with the SDK version." |

## When

Raised when the SDK's `/gate` or `/execute` call fails with something
that is **not** a transport failure — the SDK's OWN code faulted while
asking the gateway a question. The gateway may well have answered; the
SDK could not read what it got, or never got as far as asking. There is
therefore no decision to honour, and the SDK refuses the call instead of
assuming it was allowed.

This is NOT the same as a dead backend. A transport failure is
[NR-B001](NR-B001.md) / the ADR-008 fail-OPEN posture: the gateway could
not be REACHED, there is no answer to honour, and the agent must not
freeze during an outage. Here the enforcement path is un-decidable
rather than undecided — an unanswered question is not a yes.

Before this code existed, the runtime's gate handler ended in a bare
`except Exception` that failed OPEN for every fault, so an SDK-internal
error was logged and the call proceeded with no reservation: the tool
ran, the backend booked nothing, and the cost event was dropped (the
audit finding SDK-11).

The `/execute` seam is the same fact on the other side of the call
(audit finding SDK-13, ADR-131). There, the `@protect` decorator's
catch-all used to report an SDK-internal fault as **`NR-B001`** and to
type it as a **policy decision**, so a FastAPI host rendered it **HTTP
429 / category "decision"** — the operator was told the policy refused
when the truth was that the SDK had a bug. It now raises this same
code, and the two-step fail-open opt-in cannot open it.

## Common causes

1. **A request body that cannot be serialised** — `json.dumps` on the
   signed gate body raises, and the SDK never reaches the network.
2. **A decode fault** — the response body is not JSON, or a field has
   an unexpected shape.
3. **A bug in the SDK's request builder or the edge path** — a
   `KeyError` / `TypeError` / `AttributeError` raised while assembling
   or splitting the request.

## How to fix

1. **Retry** — the fault may be transient (a malformed body from one
   particular input, a race in the edge path).
2. **If it persists, report it** — the exception's `cause` carries the
   original fault and `__cause__` is set, so the traceback reaches the
   actual bug. Report it with the SDK version.
3. **Check the counter** — `gate_indeterminate_total` counts the
   `/gate` refusals and `policy_gate_indeterminate_total` counts the
   `/execute` ones. They are deliberately NOT `gate_fail_open_total`:
   that one counts calls that were allowed, these count calls that were
   stopped. A non-zero value means the SDK itself is faulting, not that
   the backend is down — and the two counters separate the two seams,
   so an operator chasing an SDK bug knows which one moved.

## Catch pattern

```python
from nullrun.breaker.exceptions import NullRunGateIndeterminateError

try:
    nullrun.init(api_key="nr_live_...")
except NullRunGateIndeterminateError as exc:
    if exc.error_code == "NR-P004":
        log.error("gate decision indeterminate: %s", exc.__cause__)
        # The SDK's own fault — surface it, do not treat it as
        # "the backend is down and the call was allowed".
        return render_sdk_fault_page()
    raise
```
