# NR-P005 — Unknown control-plane action type

| Field | Value |
|---|---|
| **Code** | `NR-P005` |
| **Category** | **P**rotocol |
| **Exception class** | `NullRunUnknownActionError` |
| **Retryable** | No |
| **Default `user_action`** | "The NullRun control plane sent an action type this SDK version does not know, so the action was NOT executed. This is a server/SDK version mismatch — upgrade the SDK to a version that understands the control plane's action vocabulary. The workflow itself is not blocked." |

## When

Raised when a control-plane action arrives whose `type` is not in the
SDK's `ActionType` enum — a wire value the SDK cannot interpret, and
therefore cannot execute.

The action dispatcher used to log the unknown type at ERROR, record a
forensic history event, and **return**. The action was then neither
executed nor refused, while the caller's own bookkeeping said it had
been handled: a control-plane instruction that is silently dropped is
a control-plane instruction that does not exist (the audit finding
SDK-12).

## Common causes

1. **A server/SDK version mismatch** — the backend grew its action
   vocabulary (`Alert | Pause | Kill | Snapshot` today) and the SDK in
   the field has not caught up. The backend emits the action type as a
   Rust `Debug` string (`"Kill"`, `"Pause"`, …), so a rename on the
   backend side becomes an unknown type on the SDK side.
2. **A control-plane schema regression** — the server sends a value
   that was never in the vocabulary.
3. **A hostile or corrupt response** — anything the SDK cannot parse.

## What it is NOT

It is deliberately **not** a `NullRunBlockedException` and **not** a
`NullRunDecision`. An unknown action type must not degrade into "the
workflow is blocked": that was the DoS amplifier the B14 fix removed —
one unrecognised value from the control plane would stop every
subsequent tool call in the workflow. The workflow keeps running; the
*action* did not run.

It is also deliberately **not** a `NullRunTransportError`. ADR-126's
two-step opt-in opens transport errors, and "the body runs" is not an
acceptable answer to "the control plane sent an instruction this SDK
cannot execute".

## How to fix

1. **Upgrade the SDK** — this is a version-alignment problem, not a
   transient fault. Retrying the same action against the same SDK
   version fails identically (`retryable` is `False` for that reason).
2. **Check the counter** — `unknown_action_total` counts these. The
   expected rate is zero; a non-zero rate means the control plane is
   sending instructions this SDK cannot run.
3. **Check the logs** — the dispatcher logs at ERROR with the action
   type and the workflow id, and the `/track/batch` call site logs the
   same event as a control-plane integrity event (not as a "skipped
   malformed action").

## Catch pattern

```python
from nullrun.breaker.exceptions import NullRunUnknownActionError

try:
    nullrun.handle_action(action_type, workflow_id, reason)
except NullRunUnknownActionError as exc:
    if exc.error_code == "NR-P005":
        log.error("control plane sent an unknown action: %s", exc.action)
        # The ACTION did not run. The workflow is NOT blocked — do not
        # turn this into a policy refusal.
        return render_version_mismatch_notice()
    raise
```
